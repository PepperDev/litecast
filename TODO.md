## HTTP serving model: Content-Length, Range, producers and consumers (DOMAIN.md §HTTP response selection, §Producers and consumers)

Re-advertise finiteness/seekability per user decision: `Content-Length` when
the total is known (file mode; completed command, with or without
`--cache-to-fs`), `Range` accepted when the client asks and the data is
retained; **the producer/consumer model is conditional on the source mode**
(DOMAIN.md §Producers and consumers):
- **file** → consumers read the file directly; no producers;
- **command + `--cache-to-fs`** → exactly ONE producer writes the file
  regardless of consumers; consumers read the file directly; `Content-Length`
  only at command completion;
- **command, no spool** → zero or more on-demand producers, zero or more
  consumers sharing producers, idle-terminated when abandoned; when the
  **first producer terminates** its `total` is stored and any further request
  may answer with `Content-Length` (file-mode rule);
LOAD `streamType` stays `LIVE` (DOMAIN.md
§Business Rule 11 history note; live CDD to confirm no `errorCode-104`
regression).

- [x] **`--no-arbitrary-range` / `-n`: on an unknown-length stream the server
  chooses the end of an open-ended `Range: bytes=N-` itself — the frontier
  (`received`) when the start is produced, or `N+1` (a one-byte reply, head
  stowed until that byte exists) when a running producer has not reached `N`
  — and the flag is the escape hatch that forbids it entirely (the request is
  then answered `200` from byte 0, the pre-trace.22 matrix)** (user decision,
  Oct 3, following the trace.22 fix `dc099ee`; a receiver that reads a short
  `206` as end-of-stream must have a way back to the whole-resource answer).
  - **Wire rule (decided).** Unknown total, open-ended `bytes=N-`, resolved to
    a producer window (`stream_avail` = retained prefix):
    - `avail ≤ N < received` → `206` + `Content-Range: bytes
      N-(received-1)/*` + `Content-Length: received−N`, finite, then close
      (unchanged from `dc099ee`).

      N-N/*` + `Content-Length: 1`, head **stowed** until byte `N` is produced

      guard (user decision): with nothing produced there is no frontier to
      promise from and a fresh producer would have to make `N` bytes before

    - `received == 0` (cold) or `N < avail` → `200` from byte 0 (rule 3).

      the last row: `200` from byte 0.

- [x] **Producer model: producer list + request-`s` resolution (no-spool
  commands only)** — replace the single command `source`/`buffer` with a
  producer list (each producer: argv, pid, own `position`, own retention

  applies ONLY to `--command` without `--cache-to-fs` (§Producers and
  consumers). File mode and command+spool are untouched here — file:
  consumers `pread` the file directly; command+spool: exactly ONE producer

  resolves its start `s` (**`0` for a plain request**) against the producers:

  nearest producer **behind** `s` and **wait for position** (unfreeze it if
  frozen, otherwise keep draining it; feed starts once the window retains

  position. A consumer closes → detach and

## Bugfixes

- [x] **A session litecast retires on purpose is never terminated on the device, and a Ctrl-C that lands in the restart backoff sends NO termination frame at all — the exit STOP is gated on the latched session handle that the retire path has already zeroed, so the DMR app is left running when the run exits** (live strace `.tmp/.trace.23`, Oct 3 19:29:06→19:31:06, **no instrumentation** — TLS only, no `.trace.23.log`, so the control plane is unreadable; no-spool `--command ffmpeg -i /tmp/v.mkv -vf subtitles=… -preset slow -maxrate 6000k -g 60`, device 192.168.0.20:8009, HTTP 34757; one `ffmpeg` child (4662) for the whole run). The user's exact report: **"Ctrl-C should still send the chromecast stream termination signal."**
  - **Trace evidence.** Five control connections to 192.168.0.20:8009 — `connect(8)` 19:29:07.219 / `close(8)` 19:29:58.599, 19:30:00.223 / 19:30:09.598, 19:30:12.219 / 19:30:24.752, 19:30:29.221 / 19:30:40.728, 19:30:49.219 / **19:31:03.461**. The close→connect gaps are 1.62 / 2.62 / 4.47 / 8.49 s — `RESTART_BACKOFF {1000,2000,4000,8000}` plus the 1 s tick granularity: the §Session supervision **restart lane** escalating, transport budget untouched (no transport loss in 2 minutes). Every retirement has the same shape: a verdict frame arrives, `munmap`×3 (TLS session + reader freed), `close(8)` **0.3 ms later** — the last outbound frame before it is a 109-b PING (`19:30:40.727595`, 0.5 ms; `19:31:01.219131`, 2.24 s), so **no receiver `STOP` was ever sent**: the run's 148 `sendto(8,…)` writes are only 1/5/32/70/83/109/113/125/139/314-b TLS records, i.e. the per-session CONNECT→GET_STATUS→LAUNCH→LOAD cadence plus PINGs. The retired session was live and pulling every time (`accept4(7,…)` = fd 11/9/11 at 19:30:50.652/.754, 19:30:52.406, 19:30:55.332 on the last one). Then `close(8)` 19:31:03.461825 books an 8 s restart (due 19:31:11.46), the ticks at 19:31:04.218 and 19:31:05.218 find nothing due, and **`SIGINT` lands 19:31:05.528** — 2 s into the 8 s backoff: `signalfd` read (128 B) → `kill(4662, SIGTERM)` 19:31:05.528764 → `SIGKILL` 19:31:06.536 → reaped 19:31:06.589 → `close(7)`, `close(10)`, `close(6/5/4)` → **`exit_group(0)` 19:31:06.591 with zero bytes written to the device after 19:31:01.219131**. The 339-b record read at 19:31:03.461492 (`0x17 03 03 01 4E` = a 324-b TLS payload) is the abandonment verdict; its content is undecryptable.
  - **Root cause.** `cast_conn_restart()` (`src/cast/conn.c:271`) and `conn_lost()` (`src/cast/conn.c:52`) retire the socket with the **same six lines**: `cast_ctrl_close(&cn->ctrl)` — which `memset`s the whole ctrl (`src/cast/ctrl.c:88`), so `state` → 0 and `session_id` → empty — then `close(fd)`. Dropping the socket therefore destroys the **only** handle litecast holds on the device's session. The exit STOP is gated on exactly that handle: `cast_ctrl_stop()` (`src/cast/ctrl.c:140`) returns 0 immediately unless `state == CTRL_READY && session_id[0] != '\0'`, so `teardown_run()`'s `(void)cast_ctrl_stop(&ctx->cn.ctrl)` (`src/main.c:269`) is a **silent no-op** here — and even on the healthy path it is issued *after* the bounded child reap, so the device keeps playing until the reap finishes (1.06 s here). DOMAIN.md §Exit promised the STOP "if a session was latched", true only while the socket is up, and no rule said who terminates a session the run retires deliberately — so trace.22's supervision (`dc099ee`, five retirements in 2 minutes) turned an edge case into the common exit path. The same hole sits on the transport lane: a heartbeat timeout or a retry-budget exhaustion aborts with the DMR still streaming a dead pull.
  - **Fix (design).** Terminate the session on the device **at the moment litecast gives up its socket**, not only at exit: before a latched ctrl's socket is closed — on **both** lanes, the §Session supervision restart and a transport loss (EOF/hard error, handshake or heartbeat timeout, budget exhaustion) — send the same best-effort receiver `STOP`. `cast_ctrl_stop()` already carries the right predicate (`CTRL_READY` + non-empty `sessionId`), so a handshake-time retire sends nothing, no new state or flag is needed, and the cost is one ~150-b frame per retirement. Design analysis (rule 0 / §Multiple consumers) pins it as a consumer-attachment/pacing defect, not a resolution-order one:
  - **Mechanism.** The byte-0 whole-resource restart (or the fresh whole-resource spawn when byte 0 was compacted) races the device's **abandoned earlier pull**: that old connection stays attached to the producer's window (HTTP connections are never closed for idleness; "an attached consumer — even a non-reading one — never triggers the guard"), so its frozen `read_off` either (a) pins `buffer_lowest` and throttles the window so the replay consumer reaches the retained end and then starves at the live edge (the re-freeze at the same content point), or (b) keeps the old producer gated-but-alive forever — a command streaming into a window no live connection reads, reaped by nothing ("the producer continued running non-stopping"). And a keep-alive / same-conn re-route can **orphan** a consumer index: `resolve_body`/`attach_at` re-calls `cvec_push`, which overwrites `c->cidx` without releasing the conn's previous claim — a ghost entry no connection owns; `cvec_pop`'s swap-remove + `reloc_consumer` can't see it (it pins compaction or unthrottles production invisibly).
  - **Fix — the re-pull is the device's only active playback; it retires the abandoned earlier pulls and owns its producer.**

    2. **Consumer-index ownership:** re-attaching a connection first releases its previous claim (detach + relocating the displaced last consumer), so no path leaves a consumer entry with no owning connection. `buffer_lowest` therefore reflects only live connections: neither a pins-compaction ghost nor an unthrottling one can exist.

- [x] **File-mode content type is `application/octet-stream` instead of the actual MIME type** (found by live device test — device shows loading page but never plays): `serve_start` (`src/main.c:92`) hardcodes `application/octet-stream` for file mode. The DMR needs the real content type (e.g. `video/mp4`) both in the LOAD `contentType` field and the HTTP Content-Type header to start playback.
